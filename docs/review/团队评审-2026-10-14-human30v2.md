## 1. 严重问题（会导致设计错误或红线违规）

### S-1 ｜🔴 **大量"自创"未标注，会被误认为原文**（角色 A）
spec 在标为"原文/照搬"的位置混入了**原文没有**的内容，实现者会当成 Dan Koe 的东西：
- **36 个问卷选项文本**（§5.2）：原文是**开放式访谈**，无选项
- **判层规则"众数/中位数"**（§5.3）：原文依 LLM 判断，无确定性算法
- **confidence 三档**、**Traits"有/少量/无→1/2/3"**（§5.5）、**相位 1 题合并**（§5.4）
- **Glitch 三级阈值 `<2.0 / 2.0~2.5 / ≥2.5`**（§5.7）：原文分级按 **Level 1.0 / 2.0 / 2.5-3.0**
- **日频 Channel 监测题**（§5.7）、**迁移分档阈值**（§4.2）
⇒ **修法**：全篇引入统一来源标记 **〔主文〕/〔Prompt〕/〔自创〕** ✓

### S-2 ｜🔴 **"原文"一词覆盖三源，来源标注错误**（角色 A）
- **Lifestyle 三层（Accidental/Designed/Integrated）与 6 个 Lifestyle Archetype
  在主文 `main.txt` 中完全没有** ✗ —— 它们出自**官方 Prompt**（`prompt.txt:298-379`）
- spec §1.9 却标"原文"；§0.1 R-8 又反复强调"原文"
- 另有《A Complete Knowledge Base》（spec 自认"未获取"）
⇒ **修法**：§1.9 等逐项标注来源，与主文区分 ✓

### S-3 ｜🔴 **Metatype 走 LLM 是相对上轮结论的"净新增"**（角色 B）
- 上轮 `团队评审-2026-10-12.md` 对红线②的结论是：**「human30 全程确定性无 LLM」**
- v2 把 **Metatype 交给 LLM 生成** ⇒ **净新增 LLM 输出点** ✗
- spec 用一句"复用**已登记**的 H-REV-001"自我豁免，但 **H-REV-001 未进 `decision-log.md`** ✗
⇒ **修法**：落地前必须在 `decision-log.md`（或 hypotheses）**正式登记**，含 🟡 标记、
   失败降级路径、输入/输出边界、**禁止入链的守卫** ✓

### S-4 ｜🔴 **删掉"追问"= 删掉原框架防自欺的核心机制**（角色 D，最深刻）
- 原文的层级判定靠 **LLM 追问**（`prompt.txt:629-637,703-705`：
  "你说你懂 X，那每天怎么用？"／"Continue probing until confident"）
- v2 改成 **12 题三选一** ⇒ **无法追问** ✗
- 且**选项自带褒贬**（L1=权威/跟风，L3=整合/使命）⇒ 结构性**社会期许偏差** ✗
- ⇒ 判出来的"层级"是**"你希望你所在的层级"** ✗，不是原文意义上的层级 ✗
- ⇒ 叠加"自己打分 + 自己解读"⇒ **系统可能成为 False Transformation 的温床** ✗✓
  （原文靠追问戳破假性转变；v2 反而用一段体面的话把它包装成"你的 Metatype 是 The Outlier" ✗）

### S-5 ｜🔴 **§14 三条联系 = 样本量个位数的伪科学包装**（角色 D）
spec §14.4 **自己承认**：「日频 1 条，『极端档位 + 失调相位』一年可能仅个位数 ⇒ 统计功效极低」
⇒ 既然自认样本不足，就**不应写进 spec 当待做功能** ✗
⇒ **修法**：§14 降级为一句备注「样本不足，仅记录不分析」，删掉"检验"列 ✓

## 8. 角色 C（工程可行性）—— 补做报告（2026-10-14 追加）

**基线纪律**：本轮明确要求**全部走 `origin/main`** ✓。
（评审员自己也踩到"非基线文件不可信"的活样本：它发现的临时 worktree
**不是** `origin/main` —— `server.py` 无 `/api/human30`、`report.py` 无 `_human30_block` ✗）

### 🔴 C-1 ｜`aggregate()["level"]` 语义变更 = **静默行为变更**
- v1 `aggregate()["level"]` = **整体均分档**（`human30.py:159-164`，`avg<40→1`）
- spec 要改成"最弱象限的层"⇒ **签名不变、key 不变、调用点不改**，但**值变了** ✗
- 消费点：`report.py:721-727`（看板主卡 `level`/`level_name`）、`invest_research.py:650-678`
  （`brief_line()` → `level_name`）、`human30_review.py:46,96-104`（`level_name.split(" ")[0]`）、
  `human30_cli.py:50`
- 后果：看板主卡会从「L2 综合者」**静默变成**「L1 从众者」，代码一个字不改 ✗
- ⇒ **修法（已落 spec §3.1）**：旧 key **保持原义** ✓；v2 另开
  `quadrant_levels` / `weakest_level`（**只增 key，不改旧 key 值**）✓

### 🔴 C-2 ｜守卫 3「无登记则 import 时 raise」会让**当前仓库全线崩**
- 当前 `decision-log.md` **无** H-REV-001 登记（grep 仅命中 L3.5 `insight_summary` 与 S-2 清理）
- 若绑在 `import human30` 上 ⇒ `test_human30.py` / `test_human30_robustness.py` /
  `test_human30_review.py` / `human30_cli.py:24` / `report.py:717,739` / `invest_research.py:654`
  **全部 raise** ✗
- ⇒ **修法（已落 spec §9.3）**：守卫 3 **只对 🟡 判层入口**检查 ✓；
  **不得**放在 import 路径 ✗；**登记先于守卫** ✓；归入 **P4** ✓

### 🔴 C-3 ｜懒迁移 vs `record()` 现有落盘逻辑 —— **会重写/重排/丢字段**
- v1 `record()`（`human30.py:133-138`）= 读全量 → 按 date 删同日旧 → append → **全量 sort** → **整文件 `_save`**
- 三个缺陷 ✗：
  1. **新增一条记录会重写并重排全部历史** ✗（与"不重写文件"矛盾）
  2. `sort(key=lambda r: r["date"])` 用 `r["date"]` 非 `r.get` ⇒ 畸形记录 **KeyError** ✗
  3. **同日二次打卡会丢字段** ✗（`rec` 只含 7 个旧字段 ⇒ v2 的
     `levels`/`phases`/`traits`/`flags`/`assessment`/`schema` 被抹掉）
- ⇒ **修法（已落 spec §4.2.1）**：`store.append()` 做「**同日合并**（深合并）」而非"删旧+append" ✓；
  序列化**保留未知字段** ✓；`r.get("date")` 防崩 ✓；**只在有变更时才写** ✓

**兼容层"签名不破"总体成立** ✓，但 **C-1/C-2/C-3 三条必须在 P1 前修掉** ✗（已全部落 spec）✓
