## 1. 严重

### S-1 ｜ `sys` 未导入却调用 `sys.executable` —— 看板后台刷新会 NameError

- **文件:行号**：`fg_system/dashboard/freshness.py:113-116`（模块导入区在 `freshness.py:18-26`）
- **严重级**：严重
- **问题**：`sys_python()` 第 116 行 `return venv if os.path.isfile(venv) else sys.executable`，但本模块**从未 `import sys`**（导入只有 `os / subprocess / threading / time / datetime / pandas / config`）。当仓库 `.venv/bin/python` 不存在（Windows 开发机正是这种情况，见 `AGENTS.md` §6 本机判据）时，`sys_python()` 抛 `NameError: name 'sys' is not defined`。`sys_python()` 在 `_run_refresh()` 第 94、102 行被调用（子进程启动 `sync_positions.py` / `fetch_shoutu_api.py`），因此看板刷新触发时会**整个后台刷新线程崩在 NameError**，且 `_run_refresh` 的 `except Exception as e`（第 109 行）只把它写进 `/tmp` 日志 —— 用户在前端**看不到任何提示**。
- **建议**：在 `freshness.py` 顶部补 `import sys`。同时把 `/tmp/fg_dashboard_fresh.log`（见 S-2 / G-2）改为跨平台路径。

### S-2 ｜ 源码树内硬编码 Hermes 会话密钥

- **文件:行号**：`scripts/evolve_review.py:39`
- **严重级**：严重
- **问题**：`HERMES_KEY = os.environ.get("API_SERVER_KEY", "32b64f3f308f403fffbe1c989acd9a9af32743a9a5e35d7a7b4d293e566f6ddc")` —— 把一长串会话密钥**明文写进源码**。`AGENTS.md` §2 与 `docs/system-boundary.md` 的红线是「**密钥禁提交**」；`fg_system/data/shoutu.py:58-82` 的 `load_token` docstring 也明确「**源码树里永远不出现密钥**」。该默认值一旦随文件入库（本仓库是 git 跟踪的 `scripts/**`），密钥即进入版本历史。此处把 `os.environ.get` 的**兜底默认值**设成真实密钥，等于让环境变量形同虚设 —— 只要 env 未设就静默用明文密钥。
- **建议**：删掉默认值，改 `HERMES_KEY = os.environ.get("API_SERVER_KEY", "")`；缺值时在 `call_llm` 里显式报错（同 `hermes_key` 缺失时的处理）。并**轮换**该密钥（已入历史即应视为泄露）。

### G-2 ｜ 硬编码 `/tmp` 路径 —— Windows 端不兼容，违反 AGENTS §6.4

- **文件:行号**：`fg_system/dashboard/freshness.py:28`（`_LOG = "/tmp/fg_dashboard_fresh.log"`）、`scripts/futu_realtime.py:327`（`lock_path = "/tmp/fg_realtime.lock"`）、`scripts/evolve_review.py:175`（`os.path.join("/tmp", ...)`）、`scripts/_kb_add_wechat.py:28`（`Path("/tmp/wx_article.txt")`）
- **严重级**：一般
- **问题**：`AGENTS.md` §6.4 明确「临时文件必须用绝对路径或 `$TEMP/`」，并记录 2026-10-10 桌面清出 51 个 `fg_*.txt` 的教训。上述 4 处把临时文件/锁文件写死到 Unix `/tmp`：在 Windows（`AGENTS.md` 声明的开发主力端，见 `docs/dual-end-workflow.md` §B）`/tmp` 通常不存在 ⇒ `freshness._log` 每次写盘失败（被 `except Exception: pass` 吞掉，见 G-4），`futu_realtime` 锁文件创建失败，`evolve_review` 的第 175 行 `open(tmp,"w")` 直接抛 `FileNotFoundError`。这是**跨端运行的真实故障点**，非风格问题。
- **建议**：统一改用 `tempfile.gettempdir()` 或 `os.environ.get("TEMP")`。`freshness` 的日志可落到 `config.DATA_DIR` 下的固定名（更便于排查）。

### G-3 ｜ 硬编码飞书 open_id 写进源码

- **文件:行号**：`scripts/invest_research.py:31`（`FEISHU_OPEN_ID = "ou_c4f5cd25e5001a853309524e899dd6d2"`）
- **严重级**：一般
- **问题**：同文件 `invest_research.py:38-68` 的 `_read_hermes_key` / `_read_nim_key` / `_read_feishu_creds` 都坚持从 `~/.hermes`、`~/.openclaw` 等**仓外配置文件**读取，docstring 第 11 行也声明「密钥全部从本机配置文件读取，源码树不出现任何密钥」。唯独 `FEISHU_OPEN_ID` 被写成常量。open_id 虽非密钥，但它绑定了**用户身份标识**，属个人可识别信息，且与「配置不落源码树」的既定纪律不一致。

### G-4 ｜ 异常被静默吞掉（多处，影响可观测性）

- **文件:行号**：
  - `fg_system/dashboard/freshness.py:41-42`（`except Exception: pass`，日志写失败被吞）
  - `fg_system/dashboard/freshness.py:53-54`（`_last_date` 解析失败返回 None，与"文件缺失"不可区分）
  - `scripts/invest_research.py:90-91`（`_okx_ticker` `except Exception: return None`）
  - `scripts/invest_research.py:337-338`（`stage_attribution` `except Exception: return None`，LLM 失败与"输出被清洗判定为空"不可区分）
  - `scripts/invest_research.py:399-400`（`_rss_titles` `except Exception: return []`）
  - `scripts/archive_briefs.py:31-32`（`except Exception: return ""`）
  - `scripts/decision_log.py:57-58, 77-78`（读 state/positions 失败返回 `{}`）
- **严重级**：一般
- **问题**：系统整体纪律是「**不静默降级**」（`pipeline.py:757` 的 `_require_series_coverage`、`loader.py` 的 `shoutu_to_system_scale` 越界即报错，都是这条纪律的正面样板）。但上述脚本层把外部调用/IO 失败一律吞成 `None` / 空值。对简报类脚本这是**有意的降级设计**（docstring 有说明），但**"调用失败"与"合法空结果"被压成同一个返回值**，使排障时无法区分。尤其 `freshness.py:41` 的日志吞异常，与 S-1 叠加后导致故障完全不可见。
- **建议**：吞异常处至少记录一行上下文（如 `print(..., file=sys.stderr)` 或写日志），或返回带原因的对象；`freshness._log` 的 `except` 不应完全静默。

### G-5 ｜ OKX 凭据经 curl **命令行参数**传递（进程列表可见）

- **文件:行号**：`scripts/sync_positions.py:184-192`（`cmd = ["curl", ..., "-H", "OK-ACCESS-KEY: " + creds["api_key"], ...]`，随后 `subprocess.run(cmd, ...)`）
- **严重级**：一般
- **问题**：API key / secret 派生的签名 / passphrase 全部作为 `curl` 的 `-H` 参数，出现在**进程命令行**中。同机任意进程（`ps aux` / Windows 任务管理器）都能读到这些凭据与签名。密钥文件本身已 `chmod 600`（`sync_positions.py:36, 204`），但这条路径把保护绕开了。同类问题见 `scripts/evolve_review.py:180-184`（NVIDIA key 作为 curl `-H` 参数）。
- **建议**：改用 Python `urllib` 直接发请求（同 `fg_system/data/fetch.py` 的做法），或把 header 写入临时文件用 `curl --config`/`-H @file` 引入，避免凭据出现在 argv。

### G-6 ｜ `datetime.utcnow()` 已废弃

- **文件:行号**：`scripts/sync_positions.py:179`（`datetime.datetime.utcnow().strftime(...)`）
- **严重级**：一般
- **问题**：`datetime.utcnow()` 在 Python 3.12+ 被标记废弃，产出**无时区**的 naive 时间。项目声明 Python 3.10（本机 `py -3.10`），当前可运行，但 OKX 签名对时间戳敏感，naive UTC 一旦与真实 UTC 偏移会直接导致签名失败。属未来兼容 + 正确性隐患。
- **建议**：改 `datetime.datetime.now(datetime.timezone.utc)` 并显式格式化。

### G-7 ｜ 守猪待兔凭据随飞书包传输（设计如此，但应复核）

- **文件:行号**：`scripts/make_feishu_bundle.py:557-562`（`keep` 包 `for rel in NEED_DATA_FILES + MANUAL_FILES`）；`MANUAL_FILES` 定义在 `scripts/check_deploy_set.py:82`（`["Data/shoutu_token", "Data/tstoken"]`）
- **严重级**：一般（**待确认**）
- **问题**：`keep` 包**有意**把 `Data/shoutu_token`、`Data/tstoken` 打入包中（代码注释第 558 行「凭据被 gitignore，靠这里带过去」），经 base64 分片走**飞书消息**传到 Mac。这是双端协作链路（`docs/dual-end-workflow.md` §C）的既定设计。风险点：凭据经**第三方 IM**中转，且分片以 URL-safe base64 明文承载，无端到端加密。是否可接受取决于公司对飞书消息通道的信任级别。
- **建议**：**待确认** —— 请用户确认「守猪待兔 token 经飞书传输」是否为有意接受的风险。若否，应改为一次性手动拷贝（`check_deploy_set.py` 的部署包路径本身就有"手动拷凭据"的机制）。报告不做裁决。

## 3. 建议

### R-1 ｜ `freshness.sys_python()` 无测试覆盖（S-1 的成因）

- **文件:行号**：`tests/dashboard/test_freshness.py:37, 51, 66`（`monkeypatch.setattr(freshness, "_run_refresh", ...)`）
- **严重级**：建议
- **问题**：三个测试全部把 `_run_refresh` 替换成 lambda，**从不**进入 `_run_refresh` 体内 ⇒ `sys_python()`（第 113-116 行）**从未被执行**。这正是 S-1 的 `NameError` 能长期潜伏的原因。测试验证的是"是否触发线程"，不是"刷新逻辑是否正确"。
- **建议**：补一条直接调用 `freshness.sys_python()` 的测试（断言返回可执行路径字符串），并补一条以 monkeypatch 子进程的 `_run_refresh` 集成测试。

### R-2 ｜ `evolve_approve.py` 用法提示与实际参数不匹配

- **文件:行号**：`scripts/evolve_approve.py:127`（提示 `--approve <file> --status Y|N|Z --log`）vs `evolve_approve.py:152-176`（`main`）
- **严重级**：建议
- **问题**：推送到飞书的消息（第 127 行）给出的命令示例，与 `main` 里 `--approve`（第 155 行，无位置参数带 file）、`--status`（第 156 行）的实际参数名能对上；但 `scan_pending` 的判定提取正则（第 57 行 `^\*\*(不采纳|提案候选)[^*]+\*\*`）只识别两种文案，且 `--approve` 分支要求 `--status` 二者同时给（第 169-171 行），而飞书提示未说明缺 `--status` 会 `exit(1)`。属**易用性/文档漂移**，会误导人工审批这一步（C-3 是人工门控关键环节）。
- **建议**：让第 127 行的提示与 `main` 的真实必填项严格一致；或为 `--approve` 补默认 `--status` 校验提示。

### R-3 ｜ `evolve_walkforward.py` 在窗口循环内重复计算变体

- **文件:行号**：`scripts/evolve_walkforward.py:100`（`fv = vmod.apply_variant(feat, pf, vk)` 位于 `for (a, b) in windows:` 循环体内）
- **严重级**：建议
- **问题**：对同一 `(feat, pf, vk)`，`apply_variant` 在整个窗口循环中被**重复调用 N 次**（N = 季度窗数），结果每次相同（它是纯函数）。属可避免的重复计算，季度窗多时浪费明显。逻辑**正确**（未引入偏差），只是效率问题。
- **建议**：把 `fv = vmod.apply_variant(...)` 提到窗口循环外，循环体内只做 `fv.loc[a:b]` 切片。

### R-4 ｜ 守猪待兔 API 密钥注释与实际 `.gitignore` 覆盖不一致（待确认）

- **文件:行号**：`scripts/fetch_stablecoin_usage.py:85-86`（注释「key 文件放 `Data/stablecoin_key` … 本仓库 `.gitignore` 已含 `Data/*token*`，故用 `Data/stablecoin_key`… 需确认已在 .gitignore」）
- **严重级**：建议（**待确认**）
- **问题**：该注释**自述**「需确认已在 .gitignore」。`Data/stablecoin_key` 不含 `token` 子串，故 `Data/*token*` 规则**不覆盖**它；`config.SHOUTU_TOKEN_PATH` 的同类约定是「必须在 .gitignore 覆盖范围内」（`config.py:475-478`）。本报告**未读取 `.gitignore` 实际内容**（该文件在根级，属"只允许新建一个文件"约束外的只读对象，但本次未核），故标待确认。
- **建议**：**待确认** —— 核对 `.gitignore` 是否显式含 `Data/stablecoin_key`。若无，补一行；同时移除源码里"需确认"的不确定注释。

### R-5 ｜ 死代码/兼容层长期保留，缺退役标记

- **文件:行号**：`fg_system/signal/legacy.py`（整文件，v1 逐字副本）、`fg_system/pipeline.py:310-313`（`signal_wide` docstring 自述「目前只有使用方 1」）、`fg_system/cli.py:281-283`（回测基准数字**硬编码**并注明「改动加密层配置时必须同步更新此字符串」）

- **建议**：为 `legacy.py` 加一个明确的退役条件/TODO（否则会永久堆积）；`cli.py` 的回测基准数字改为从 `evolution/` 的 baseline 读取或加自动校验。

### R-6 ｜ NewsAPI key 置于 URL query string

- **文件:行号**：`scripts/fetch_news.py:69`（`url = f"{API}?q=...&apiKey={key}"`）
- **严重级**：建议
- **问题**：key 明文拼进 URL。经代理（第 63-65 行走 PROXY）或服务端访问日志时会残留。NewsAPI 官方即用 query string（无法改 header），故属**约束所致**，但仍应在日志/异常里避免回显完整 URL。

### R-7 ｜ `check_freshness.py` 只写不删，且退出码恒为 0

- **文件:行号**：`scripts/check_freshness.py:52-55`
- **严重级**：建议
- **问题**：无论有无告警，`main()` 都正常返回（无 `sys.exit` 非零）；告警只落 `Data/freshness_warning.txt`。若每日链后续步骤依赖退出码发现停更，则拿不到信号（只能靠读文件）。属设计选择，但结合 G-1（看板不读该文件）后，停更的**唯一可见出口**只剩简报。
