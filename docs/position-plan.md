## 为什么需要

用户 2026-10-30 复盘三季度财报季：在杠杆 ETF 上采用「越跌越买」，
造成 AXTX **-78%**、CRCG -44% 的深度浮亏 ✗。原则应为「**少赚少亏但不能巨亏**」✓。

**数学依据（本条成立的根本原因）**：

| 当前浮亏 | 回本需要涨 |
|---|---|
| -20% | +25% |
| -33% | +50% |
| **-50%** | **+100%** |
| -75% | +300% |
| **-78%（AXTX 现状）** | **+355%** |

杠杆 ETF 的回本要求是**指数级**恶化的 ✗，且震荡市还有 vol decay ✗
⇒ 「越跌越买」在杠杆 ETF 上是**负期望** ✓。

## 参数（初版）

| 参数 | 值 | 依据 |
|---|---|---|
| 单标的上限 | 净值 **12%**，且取 `min(12%, 1% 规则)` | 1% 规则通常更严 ✓ |
| 杠杆 ETF 总敞口 | 净值 **20%** | 与纪律 5.2 / 5.3 相容 ✓ |
| 同时持有标的 | **≤ 2** | 20% ÷ 12% ✓ |
| 首建 | 净值 **6%** | 用户原意 $1000（约 7.3%），降到 6% 留加仓空间 ✓ |
| 加仓 | **2 档 × 3%** | 6+3+3 = 12% 正好打满 ✓ |
| 加仓间距 | `1.5 × ATR20(**正股**) × 杠杆倍数` | 纪律 4C.4 口径 ✓ |
| 相邻操作间隔 | **≥ 5 个交易日** | 纪律 5.1 ✓ |
| 触发条件 | 守猪待兔系数 ≤ **-80** **且** 跌幅达标 | AND，缺一不加 ✓ |
| 浮亏硬线 | **> 50% ⇒ 禁止加仓** | 回本数学 ✓ |

**为什么加仓只有 2 档**：纪律 5.3「单月 ≤ 4 次操作」⇒ 首建 + 2 次加仓 = 3 次，
留 1 次给「减仓至上限」✓。若用 3 档，月额度会被加仓吃满 ✗。

**为什么间距用正股 ATR**：纪律 4C.4 明确「杠杆 ETF 自身波动含损耗噪声，会污染风险估计」✗。
固定百分比也不行 —— AXTX（AXTI 2x，ATR≈8%）算出 24%，YINN（FXI 3x，ATR≈1.5%）算出 6.75%，
固定 8% 会让 AXTX 一天打完、YINN 半年不动 ✗。

## 三条硬约束（不满足就不动手）

1. **系数 ≤ -80 且跌幅达标** —— 单看系数不够 ✗（-80 可能连续多日成立 ✗）
2. **超限即冻结加仓** —— 市值已超单标的上限时**禁止**任何加仓 ✗
   （否则与「减仓至上限」互相打架 ✗）
3. **浮亏 > 50% 只禁加仓、不清仓** —— 用户 2026-10-30 明确裁定 ✓
   （**本条不授权清仓** ✗，清仓仍需人工决定 ✓）

## 2026-10-30 追加：1% 规则的 ATR 口径改为「底层 ATR × 杠杆」

**改前**：`position_limit` 用**杠杆 ETF 自身**的 ATR20 ✗ ——
违反纪律 4C.4「波动率用无杠杆底层算，ETF 自身波动含损耗噪声」✗。
后果：YINN 自身日波动 ≈ 3×FXI ⇒ ATR 被放大 ⇒ 上限被压到 $1,253（市值 $3,344，永远超限 ✗）。

**改后**：`risk.atr_pct_effective()` = `ATR20(底层) × 杠杆倍数` ✓

| 做法 | 问题 |
|---|---|
| 用 ETF 自身 ATR ✗ | 含 vol decay / 费用 / 跟踪误差噪声（违反 4C.4） |
| 直接用底层 ATR ✗ | 低估风险 3 倍 ⇒ 上限被放宽 3 倍 ⇒ **悄悄放松风控** ✗ |
| **底层 ATR × L** ✓ | 保留真实波动幅度、去掉噪声 ✓ |

实现：`fg_system/risk.py::atr_pct_effective` / `atr_pct_underlying`，
调用点：`scripts/invest_research.py`（简报）与 `fg_system/dashboard/report.py`（看板）。

⚠️ 建仓间距用的是**未乘杠杆**的底层 ATR（`atr_pct_underlying`）——
`position_plan.gap_pct()` 内部自己会乘杠杆 ✓，传有效值会导致杠杆被乘两次 ✗。

## 2026-10-30 守猪待兔历史抓取排查：**结论是服务端没数据，停止深挖**

四轮排查（每轮都在 Mac 上实测）：

| 轮次 | 假设 | 实测结果 |
|---|---|---|
| 1 | 没切到历史 tab | 补 `tab=-1` 后仍 `data: []` ✗ |
| 2 | 页面发两次请求、取错了 | 只捕获到 1 个 history 请求 ✗ |

| 4 | 要点「历史」页签 + 抓响应体 | 点到了 `OK:历史贪恐指数` ✓，点击后**无新请求** ✗ |

第 4 轮抓到的原始响应：

```
GET /api/invest/license_like?stock_id=875
    → {"status":1,"msg":"成功","data":{"status":0}}
GET /api/invest/stock_emotion/history?code=US.YINN
    → {"status":1,"msg":"成功","data":[]}          ← 服务端明确说「成功」但数据为空
```

**结论**：端点正确、鉴权正常、请求成功（`status:1`），但**服务端对该 code 返回空数组** ✗
⇒ **不是抓法问题，是服务端没有数据** ✓

旁证：`Data/raw/shoutu_history.csv` 最新只到 **2026-10-14**，而排查当天是 10-30
⇒ 16 天前还有数据、之后就没有 ⇒ 大概率是服务端在 10 月中改了接口或清了历史 ✗

**处置**：
1. `scripts/fetch_shoutu_history.py` 的 `--ids` / `--click-tab` / `--capture-all` 全部保留 ✓
   （服务端哪天恢复，直接跑即可，无需再改代码）
2. **停止继续深挖** ✗ —— 边际收益已经很低
3. 回测继续用现有数据（2024-04 → 2026-10-14，6 标的各 560~642 天）✓
